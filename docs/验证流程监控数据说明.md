# 验证流程监控数据说明

## 问题概述

当前验证监控界面显示的数据存在以下问题：

1. **Search输入值跳变**：Search的输入值应该持续累加（从运行开始至今生成的所有因子数），但会从较大数值突然跳到小数值
2. **其他阶段数据不变化**：Replay、Validation、Demo三个阶段的输入和输出值应该实时变化，但显示为固定值

## 数据存储结构

### 数据库表：validation_pipeline_data

```sql
CREATE TABLE validation_pipeline_data (
    id SERIAL PRIMARY KEY,
    symbol VARCHAR(16),           -- 品种代码
    generation INTEGER,           -- 进化代数
    -- Search 阶段
    search_input INTEGER,         -- 输入因子数
    search_output INTEGER,        -- 输出因子数
    search_drop INTEGER,          -- 淘汰因子数
    -- Replay 阶段
    replay_input INTEGER,         -- 输入因子数
    replay_output INTEGER,        -- 输出因子数
    replay_drop INTEGER,          -- 淘汰因子数
    -- Validation 阶段
    validation_input INTEGER,    -- 输入因子数
    validation_output INTEGER,   -- 输出因子数
    validation_drop INTEGER,     -- 淘汰因子数
    -- Demo 阶段
    demo_input INTEGER,           -- 输入因子数
    demo_output INTEGER,          -- 输出因子数
    demo_drop INTEGER,           -- 淘汰因子数
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    UNIQUE(symbol, generation)   -- 每个品种每代只有一条记录
);
```

**关键设计**：每个品种的每一代只有一条记录，更新时是**直接覆盖**，不是累加。

## 各阶段数据含义和计算逻辑

### 1. Search 阶段（搜索）

#### 数据含义

- **search_input**：从进化开始至今，累计生成的所有因子表达式总数
  - 应该是**单调递增**的（只增不减）
  - 包括初始种群和每一代生成的所有后代
  - 即使有重复因子也要计入

- **search_output**：当前代经过去重后的唯一表达式数量
  - 是当前种群中不重复的表达式数量
  - 每代可能不同，取决于去重结果

- **search_drop**：被淘汰的因子数量
  - 计算公式：`search_drop = search_input - search_output`
  - 主要是因为重复表达式被去重

#### 当前实现代码

```python
# evolution_center.py 第460-462行
search_input = self.total_generated_count  # 累计生成的所有因子数（只增不减）
search_output = getattr(stats, "unique_expressions", 0)  # 唯一表达式数
search_drop = max(0, search_input - search_output)
```

#### 问题分析

**问题1：search_input跳变**
- `total_generated_count` 在进化重启时可能被重置
- 如果进化进程被停止后重新启动，`total_generated_count` 会从0重新开始
- 导致前端显示的search_input从大数值突然跳到小数值

**问题2：search_output计算错误**
- `unique_expressions` 是当前种群中唯一表达式的数量
- 但search_output应该是Search阶段输出的因子数量，不是当前种群的唯一表达式数
- 这两个概念不同：Search输出是去重后的候选因子，种群唯一表达式是当前存活个体的唯一性

### 2. Replay 阶段（回放）

#### 数据含义

- **replay_input**：进入Replay阶段的因子数量
  - 应该等于Search阶段的输出
  - 即：`replay_input = search_output`

- **replay_output**：通过风险筛选的因子数量
  - 筛选条件：夏普比率 > 1.5，最大回撤 < 20%，胜率 > 55%
  - 是当前种群中满足风险条件的个体数量

- **replay_drop**：未通过风险筛选的因子数量
  - 计算公式：`replay_drop = replay_input - replay_output`

#### 当前实现代码

```python
# evolution_center.py 第465-474行
replay_input = search_output
replay_candidates = [
    ind for ind in self.gp.manager.population
    if hasattr(ind, 'fitness') and 
    ind.fitness.get('sharpe', 0) > 1.5 and
    ind.fitness.get('max_drawdown', 1) < 0.20 and
    ind.fitness.get('win_rate', 0) > 0.55
]
replay_output = len(replay_candidates)
replay_drop = max(0, replay_input - replay_output)
```

#### 问题分析

**问题：replay_input应该累加**
- 当前实现：`replay_input = search_output`（当前代的search_output）
- 应该实现：`replay_input` 应该是累计进入Replay阶段的因子总数
- 类似search_input，应该持续累加，而不是每代重置

**问题：replay_output计算方式**
- 当前是基于当前种群的风险筛选
- 但实际上Replay阶段应该是对Search输出的因子进行历史回测和风险筛选
- 当前实现混淆了"当前种群"和"Replay阶段输出"的概念

### 3. Validation 阶段（验证）

#### 数据含义

- **validation_input**：进入Validation阶段的因子数量
  - 应该等于Replay阶段的输出
  - 即：`validation_input = replay_output`

- **validation_output**：通过过拟合检验的因子数量
  - 检验指标：PBO、DSR、WFE
  - 通过所有检验的因子数量

- **validation_drop**：未通过过拟合检验的因子数量
  - 计算公式：`validation_drop = validation_input - validation_output`

#### 当前实现代码

```python
# evolution_center.py 第477-486行
validation_input = replay_output
if self.final_factors:
    validation_passed = sum(
        1 for f in self.final_factors 
        if f.overfitting_passed and f.ind in replay_candidates
    )
else:
    validation_passed = 0
validation_output = min(validation_passed, validation_input)
validation_drop = max(0, validation_input - validation_output)
```

#### 问题分析

**问题1：validation_input应该累加**
- 类似replay_input，应该累计进入Validation阶段的因子总数
- 而不是每代的replay_output

**问题2：validation_output计算错误**
- 当前使用`self.final_factors`，这是进化完成后的最终因子
- 但在进化过程中，`final_factors`可能为空或未更新
- 应该基于当前代的过拟合检验结果

**问题3：逻辑混乱**
- 代码检查`f.ind in replay_candidates`，但`final_factors`中的`FactorRecord`没有`ind`属性
- 这个逻辑在运行时会失败

### 4. Demo 阶段（演示）

#### 数据含义

- **demo_input**：进入Demo阶段的因子数量
  - 应该等于Validation阶段的输出
  - 即：`demo_input = validation_output`

- **demo_output**：最终保留的因子数量
  - 最多保留20个优质因子
  - 用于实际交易或进一步分析

- **demo_drop**：未进入Demo的因子数量
  - 计算公式：`demo_drop = demo_input - demo_output`

#### 当前实现代码

```python
# evolution_center.py 第488-491行
demo_input = validation_output
demo_output = min(demo_input, 20)  # 最多保留20个
demo_drop = max(0, demo_input - demo_output)
```

#### 问题分析

**问题：demo_input应该累加**
- 类似其他阶段，应该累计进入Demo阶段的因子总数
- 而不是每代的validation_output

## 核心问题总结

### 问题1：数据更新逻辑错误

**当前逻辑**：
```python
# validation_pipeline.py 第39-55行
if existing:
    # 更新现有记录 - 直接覆盖，不累加
    existing.search_input = search_input
    existing.search_output = search_output
    # ...
```

**问题**：
- 每代数据直接覆盖上一代数据
- 前端查询最新一代数据时，只能看到当前代的数据
- 无法看到累计的历史数据

**应该的逻辑**：
- Search输入应该是从进化开始至今的累计值
- 其他阶段的输入也应该是累计值
- 只有输出和淘汰是当前代的瞬时值

### 问题2：数据概念混淆

**混淆点1：种群 vs 流程**
- 当前实现混淆了"当前种群状态"和"验证流程数据"
- 种群状态是瞬时的（当前代的个体）
- 验证流程数据应该是累计的（从开始到现在的历史）

**混淆点2：最终因子 vs 当前代因子**
- `final_factors`是进化完成后的最终优质因子
- 在进化过程中应该使用当前代的检验结果
- 不应该等到进化完成才计算验证流程数据

### 问题3：累计计数器重置

**问题**：
- `total_generated_count`在进化重启时被重置
- 导致search_input从大数值跳到小数值

**应该**：
- 累计计数器应该持久化到数据库
- 即使进化重启，也能从数据库读取之前的累计值
- 确保数据的连续性

## 正确的数据计算逻辑

### Search 阶段

```python
# search_input：累计生成的所有因子数（从数据库读取历史值 + 当前代新增）
search_input = self._get_cumulative_search_input() + current_generation_generated

# search_output：当前代去重后的因子数
search_output = len(unique_expressions_this_generation)

# search_drop：当前代被淘汰的因子数
search_drop = current_generation_generated - search_output
```

### Replay 阶段

```python
# replay_input：累计进入Replay阶段的因子数
replay_input = self._get_cumulative_replay_input() + search_output

# replay_output：当前代通过风险筛选的因子数
replay_output = len(risk_filtered_candidates)

# replay_drop：当前代未通过风险筛选的因子数
replay_drop = search_output - replay_output
```

### Validation 阶段

```python
# validation_input：累计进入Validation阶段的因子数
validation_input = self._get_cumulative_validation_input() + replay_output

# validation_output：当前代通过过拟合检验的因子数
validation_output = len(overfitting_passed_candidates)

# validation_drop：当前代未通过过拟合检验的因子数
validation_drop = replay_output - validation_output
```

### Demo 阶段

```python
# demo_input：累计进入Demo阶段的因子数
demo_input = self._get_cumulative_demo_input() + validation_output

# demo_output：当前代最终保留的因子数
demo_output = min(validation_output, 20)

# demo_drop：当前代未进入Demo的因子数
demo_drop = validation_output - demo_output
```

## 前端显示逻辑（2026-05-31 更新）

### 核心原则
**所有阶段的输入和输出都是累计值，反映从进化开始至今的总和**

### 当前显示逻辑

前端从validation_pipeline_data表读取所有代数据，实时计算累计值：
```python
# evolution_cycles.py
all_pipeline_data = session.execute(
    select(ValidationPipelineData).where(
        ValidationPipelineData.symbol == symbol
    ).order_by(ValidationPipelineData.generation)
).scalars().all()

# 计算累计值（输入和输出都累计）
cum_search_input = sum(d.search_input for d in all_pipeline_data)
cum_search_output = sum(d.search_output for d in all_pipeline_data)
cum_replay_input = sum(d.replay_input for d in all_pipeline_data)
cum_replay_output = sum(d.replay_output for d in all_pipeline_data)
cum_validation_input = sum(d.validation_input for d in all_pipeline_data)
cum_validation_output = sum(d.validation_output for d in all_pipeline_data)
cum_demo_input = sum(d.demo_input for d in all_pipeline_data)
cum_demo_output = sum(d.demo_output for d in all_pipeline_data)

# 前端显示的累计值
search_input = cum_search_input  # 累计所有代的search_input
search_output = cum_search_output  # 累计所有代的search_output
replay_input = cum_replay_input  # 累计所有代的replay_input
replay_output = cum_replay_output  # 累计所有代的replay_output
validation_input = cum_validation_input  # 累计所有代的validation_input
validation_output = cum_validation_output  # 累计所有代的validation_output
demo_input = cum_demo_input  # 累计所有代的demo_input
demo_output = cum_demo_output  # 累计所有代的demo_output
```

### 前端显示规范
- Search输入：累计所有代的search_input
- Search输出：累计所有代的search_output
- Replay输入：累计所有代的replay_input
- Replay输出：累计所有代的replay_output
- Validation输入：累计所有代的validation_input
- Validation输出：累计所有代的validation_output
- Demo输入：累计所有代的demo_input
- Demo输出：累计所有代的demo_output

## 总结

### 当前问题

1. **Search输入跳变**：累计计数器在重启时重置
2. **其他阶段不变化**：数据更新逻辑错误，直接覆盖而非累加
3. **概念混淆**：种群状态 vs 流程数据，最终因子 vs 当前代因子
4. **数据不连续**：每代数据独立，无法看到累计趋势

### 根本原因

- 数据库表设计为每代一条记录，更新时直接覆盖
- 缺少累计字段的持久化
- 计算逻辑混淆了瞬时值和累计值

### 解决方案

1. 添加累计字段到数据库表
2. 修改计算逻辑，区分累计值和瞬时值
3. 累计计数器持久化到数据库
4. 前端显示累计值和当前代值的组合
